## Definition

An executable skill library is a key-value store where:

- **Values** are executable programs (Voyager uses JavaScript wrapping Mineflayer's Minecraft API; analogous instantiations exist in Python, shell, or any executable code) that, when invoked in the environment, perform a temporally extended skill (e.g., `combatZombieWithSword()`, `craftStoneShovel()`).
- **Keys** are dense embeddings of the natural-language *description* of each skill (Voyager uses `text-embedding-ada-002`). The description is generated by the same LLM that wrote the code.

The library is **append-only at commit time**: a new skill is added only after a self-verification critic confirms the program succeeded on its target task. **Retrieval** happens at code-generation time: the embedding of the current task plan plus environment feedback is used to fetch top-k related skills, which are injected as in-context examples into the next code-generation prompt.

The crucial property is **compositionality**: because skills are executable code, a complex new skill (`combatZombieWithSword()`) can directly call simpler stored skills (`craftStoneSword()`, `craftStoneShovel()`'s tool-acquisition sub-pattern) by reference, rather than by re-deriving their reasoning.

## Intuition

The choice of *program* (rather than token, plan, or trajectory) as the action-space matters for three reasons:

1. **Compositional reuse.** A program can name and call another program; trajectories and plans cannot.
2. **Interpretability and audit.** A library of named JavaScript functions is human-readable; a library of model weights or trajectories is not.
3. **Resistance to catastrophic forgetting.** Because the library lives outside the model and is read-only at inference, old skills survive every update. The model is frozen; the library grows.

Embedding-indexed natural-language retrieval is what lets the library scale beyond the LLM's context window: instead of stuffing every prior skill into the prompt, only the most semantically relevant few enter context for any given task.

## Variants

- **Code-as-skill (Voyager).** JavaScript via Mineflayer; one skill per file, indexed by description embedding.
- **Trajectory-as-skill** (JARVIS-1, Generative Agents memory): stores past episodes verbatim; less compositional, requires more retrieval at each step.
- **Natural-language-as-skill** (LATS, Reflexion lessons): stores textual lessons rather than executable code; cannot be invoked directly.
- **Workflow-as-skill** (Agent Workflow Memory, Cradle): stores structured workflow descriptions with explicit slots; intermediate between raw code and pure NL.
- **Hierarchical skill libraries:** skill calls skill (composed in Voyager via direct JS function calls) versus flat libraries (one-level lookup only).

## Comparison

- **vs. plan / trajectory memory:** plans and trajectories replay verbatim past episodes; an executable skill library generalizes by virtue of being parameterized code.
- **vs. classical RL skill discovery** (options framework, hierarchical RL): RL skills are policies in weight space; executable skills are in code space — far easier to introspect, transfer between agents, and version-control.
- **vs. tool libraries** (Toolformer, ToolBench): tools are pre-authored by humans; executable skill library entries are **agent-authored** at run time.
- **vs. [[procedural-skill]] (Skill-Pro):** Procedural Skills add explicit activation and termination conditions; Voyager's library entries are functions with implicit activation (the LLM decides via retrieval-and-call) and explicit termination (the program returns).

## Known limitations

- **Append-only.** The library grows indefinitely; the paper does not study retirement, deduplication, or compaction policies.
- **No post-commit refinement.** Once a skill is committed it is not revised, only superseded by composition. This is "accumulation" rather than "evolution" of skills.
- **Retrieval collapse risk at scale.** Embedding-based retrieval becomes noisy as the library grows; the paper tests up to a few hundred skills, not thousands.
- **Code-language coupling.** The skill format is bound to JavaScript + Mineflayer; porting to a new domain requires reimplementing control primitives and re-grounding the LLM in the new API.
- **Single user.** All skills come from one agent's trajectory; multi-agent shared-library settings (see [[collective-skill-evolution]]) are not studied here.

## Open problems

- **Skill refinement / evolution.** Should committed skills ever be rewritten after later failures expose bugs? The line between "edit existing skill" and "commit a new replacement" is unresolved.
- **Library compaction.** Principled retirement, merging, and deduplication policies as the library reaches thousands of entries.
- **Cross-agent transfer.** Voyager's ablation shows another agent (AutoGPT) can benefit from Voyager's library — but no general protocol exists for library hand-off across LLM backbones with different code idioms.
- **Hierarchical indexing.** Flat embedding lookup wastes structure that explicit skill-call graphs would expose.

## Relationship to foundations

Builds on program synthesis (DreamCoder, code-as-policies) for the choice of programs as the action space; on retrieval-augmented generation for the embedding-indexed lookup; on the options framework in hierarchical RL for the broader idea of temporally extended actions.

## My understanding

The choice of "code as the action representation" is what allows everything else in Voyager to work. Compositionality, interpretability, and resistance to forgetting all fall out of representing skills as functions in an external store rather than as policies in model weights. The ablation that removing the library causes the agent to plateau in late iterations is the empirical evidence that the library is not just a convenience but the **structural mechanism for long-horizon capability growth**.

The unresolved tension is between *accumulation* (library always grows) and *evolution* (skills get refined). Voyager's library only accumulates. The papers that follow it (Memp, CASCADE, SkillFlow, Memento-Skills) try to address this gap with patch, refine, or replace policies — but no consensus yet on the right lifecycle abstraction.
